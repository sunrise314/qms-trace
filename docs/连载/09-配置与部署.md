# 配置与部署

## 一、场景：代码写完了，怎么让它跑起来

前面八章把 QMS 的能力讲透了——6 张表、三个引擎、检验流程、SPC、处置规则、8D。但王主任不关心这些类怎么设计，他只关心一件事："**这套东西我怎么装进厂里、跑起来、给我的人用？**"一个能讲不能跑的系统没有价值。

这一章讲"点着它"——`application-qms.yaml` 里每一行配置是干什么的、端口为什么定在 8092、`QmsConfiguration` 这个自动配置类到底做了什么、pom 为什么"一个算法库都不引"、以及最关键的一个工程决策：**这套 QMS 是作为独立服务跑，还是作为已有芋道工程的一个子模块集成进去？** 这两条路各自怎么走。

先说明一点背景：SCADA、APS、QMS 三个模块我都用同一套芋道（ruoyi-vue-pro）脚手架、都连同一个 PostgreSQL。所以这一章的配置和部署，和前两个模块**是一套语言**——这也是自研相对买商用套件最大的隐性收益：**运维只有一套**。

## 二、application-qms.yaml：每一行都要说清

配置文件的全部内容就这么几行：

```yaml
# yudao-module-qms/src/main/resources/application-qms.yaml
server:
  port: ${QMS_PORT:8092}

spring:
  application:
    name: yudao-module-qms
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:blog}
    username: ${DB_USER:halo_pg}
    password: ${DB_PASSWORD:HaloPg_2026_x9k2}
    driver-class-name: org.postgresql.Driver
```

逐行拆。

**`server.port: ${QMS_PORT:8092}`** —— 端口用**环境变量占位符 + 默认值**的写法。`${QMS_PORT:8092}` 的语义是"先读环境变量 `QMS_PORT`，读不到就用默认的 8092"。这是**十二要素应用**（12-Factor App）的标准做法：本地开发不设环境变量，直接用 8092；生产环境用 Docker/K8s 注入 `QMS_PORT` 覆盖。**同一份配置文件，本地和生产两套值**，不用改代码也不用维护两份 yaml。

**`spring.application.name: yudao-module-qms`** —— 服务名。这个名字在集成部署时很重要：作为微服务注册到 Nacos 时，它是服务发现的 key；在日志里它是"哪个模块出的错"的标识。和 SCADA、APS 用各自名字区分开，一套日志平台里能按模块切。

**`spring.datasource`** 四项——url、username、password、driver，同样全是"环境变量 + 默认值"。url 拆成 `DB_HOST / DB_PORT / DB_NAME` 三段，用户名 `DB_USER`、密码 `DB_PASSWORD`。默认值 `jdbc:postgresql://localhost:5432/blog`、用户 `halo_pg`——这是本地开发连的库。

这里有个红线要强调：**配置文件里的默认密码（`HaloPg_2026_x9k2`）是给本地开发用的唯一兜底值，生产环境的真实密码必须走环境变量注入，绝不写进代码、绝不提交**。我在仓库里保留这个默认值，是因为它是"dev fallback"——默认值本身是公开的、只对本地有意义；真实的生产库密码是另一套，通过 `DB_PASSWORD` 环境变量注入。这和 workspace 里那条"不要把密码等重要参数上传"是对上的：**默认值可提交（本地无害），真实值只走 env（生产安全）**。

**`driver-class-name: org.postgresql.Driver`** —— 显式指定 PostgreSQL 驱动。为什么不用 Spring Boot 的自动推断？因为显式写死能避免"类路径里同时有 MySQL 和 PG 驱动时推断错"的坑。我们明确只用 PostgreSQL，显式声明更稳。

**`QMS_PORT:8092` 这个默认端口不是我随手挑的。** 三个模块的端口是一张表规划好的：

| 模块 | 端口 | 说明 |
|------|------|------|
| SCADA | 8090 | 设备数据采集 |
| APS | 8091 | 智能排产 |
| QMS | 8092 | 质量追溯 |

连号排下来有三个好处：**一是**一眼记得住（8 字头是"制造系列"，QMS 是三号）；**二是**不撞常见端口（80/443/8080/3306/5432 这些系统级端口全避开）；**三是**集成进一个工程时，如果三个模块都作为独立服务跑，端口不冲突。定端口看着是小事，但**端口冲突是部署时最常见的低级事故**，规划好名字和端口，能省掉很多排查。

## 三、QmsConfiguration：一个模块的"启动开关"

配置类的内容：

```java
// config/QmsConfiguration.java
/**
 * QMS 模块自动配置。
 *
 * yudao 父工程的 @SpringBootApplication 会扫描 cn.iocoder.yudao.module.qms 包，
 * 所以本类的主要作用是：
 * 1. 确保 qms 包被 Spring 扫描到（组件注册）
 * 2. 明确 @MapperScan 指定 MyBatis Mapper 扫描路径
 *
 * AQL 抽样方案表、SPC 控制图系数表均内置在 framework 层（纯 Java 常量），
 * 无需在此注册额外 Bean；商用扩展点（如把 AQL 主表配置化到数据库）可在此引入。
 */
@SpringBootApplication(scanBasePackages = "cn.iocoder.yudao.module.qms")
@MapperScan("cn.iocoder.yudao.module.qms.dal.mysql")
public class QmsConfiguration {
}
```

这个类只干两件事，但两件都关键。

**第一件事：`scanBasePackages = "cn.iocoder.yudao.module.qms"`。** `@SpringBootApplication` 默认只扫描**它自己所在包及其子包**。`QmsConfiguration` 在 `cn.iocoder.yudao.module.qms.config` 包下，默认扫描范围就是 `config` 包——**Service、Controller、Mapper 全扫不到**。显式指定 `scanBasePackages = "cn.iocoder.yudao.module.qms"` 把这个范围上提到模块根包，才能把 `service/`、`controller/`、`framework/` 下的所有 `@Service`、`@RestController` 组件注册进容器。

**第二件事：`@MapperScan("cn.iocoder.yudao.module.qms.dal.mysql")`。** MyBatis 的 Mapper 接口（如 `QmsBatchMapper`）是**接口不是类**，Spring 扫不到接口。`@MapperScan` 告诉 MyBatis "去这个包下找所有 Mapper 接口，给它们生成动态代理实现"。少了它，注入 `QmsBatchMapper` 就会报"找不到 Bean"。

为什么这个类**既是 `@SpringBootApplication` 又挂 `@MapperScan`**？因为它同时想支持两种部署形态：作为**独立服务**时，它是整个应用的启动类（`@SpringBootApplication` 生效，`main` 方法在的话就能 `java -jar` 起）；作为**yudao 子模块**集成时，`@SpringBootApplication` 由父工程负责，这个类里的 `scanBasePackages` 和 `@MapperScan` 仍然提供模块级的扫描范围。**一个类兜住两种形态**，这是它的设计意图。

类注释里还有一句值得注意："AQL 抽样方案表、SPC 控制图系数表均内置在 framework 层（纯 Java 常量），无需在此注册额外 Bean"。这是在回答一个常见的疑问——**为什么三张 AQL 表、三个 SPC 系数数组是硬编码常量而不是配置**？因为它们是**标准表**（GB/T 2828.1、控制图系数表），本质是"国标里的常数"，不是"客户可调的参数"。硬编码换来"零配置、开箱即用"。而注释也留了口子："商用扩展点（如把 AQL 主表配置化到数据库）可在此引入"——如果客户要自定义 AQL 表，这里就是挂配置的地方。

## 四、pom.xml：一个算法库都不引

QMS 模块的 `pom.xml`，依赖部分最值得讲的是那句**大写的注释**：

```xml
<!-- ==================== 无第三方算法依赖 ==================== -->
<!-- QMS 的三大引擎（AQL 抽样查表 / 批次谱系 BFS / SPC 统计计算）全部用纯 Java 实现，
     不引入 Timefold 等求解器或 commons-math3，减少依赖体积与升级风险。 -->
```

除了这句注释，依赖清一色是芋道标配：

```xml
<dependency>
    <groupId>cn.iocoder.boot</groupId>
    <artifactId>yudao-spring-boot-starter-biz-web</artifactId>
</dependency>
<dependency>
    <groupId>cn.iocoder.boot</groupId>
    <artifactId>yudao-spring-boot-starter-biz-security</artifactId>
</dependency>
<dependency>
    <groupId>cn.iocoder.boot</groupId>
    <artifactId>yudao-spring-boot-starter-biz-mybatis</artifactId>
</dependency>
<dependency>
    <groupId>cn.iocoder.boot</groupId>
    <artifactId>yudao-spring-boot-starter-biz-tenant</artifactId>
</dependency>
```

四个 starter 分别管：**web**（REST + 全局异常/返回包装）、**security**（认证鉴权）、**mybatis**（ORM + 分页 + 多租户拦截 + 软删除）、**tenant**（多租户上下文）。再加上 `yudao-module-system-api`、`yudao-module-infra-api` 两个模块 API（要用户/权限/字典等基础能力），以及 Lombok、测试依赖。**没有 Timefold、没有 commons-math3、没有图算法库、没有统计库**。

为什么这么"抠"？三个模块共享一个工程时，**外部依赖的每个库都是"连坐"的**——一个库升级，三个模块一起受影响；一个有 CVE，三处都要改版本。把 QMS 的算法依赖压到零，意味着 QMS 的**业务代码和外部生态解耦**——哪怕将来换了别的框架，三个引擎（`SamplingPlanEngine`、`GenealogyGraph`、`SpcCalculator`）是纯 `static` 方法，**一行都不用改**。这是"手写算法"换来的**可移植性和可测试性**：可以脱离 Spring 单元测试，也可以整个拷到别的项目。

对照 APS——APS 引了 Timefold（排产求解器是个真的重算法，手写不现实），QMS 则全是"查表、BFS、均值"这类轻计算，手写更划算。**引不引库，取决于算法的真实复杂度**，不取决于"是不是算法"。

## 五、集成与部署：两条路怎么走

QMS 有两张脸，对应两条部署路径。

**路径 A：作为独立服务跑。** 把 `yudao-module-qms` 打成一个 jar，`java -jar` 起在 8092 端口，连自己的库。适合"只想上 QMS、不想动别的"的场景。这种形态下，`QmsConfiguration` 就是启动类，`@SpringBootApplication` 直接生效。

**路径 B：作为 yudao 子模块集成。** 把这个模块作为依赖加进一个统一的 yudao 应用工程，和 system/infra 等其他模块一起跑在同一个进程、同一个端口，按 `/api/admin/qms/**` 的路径前缀区分路由。适合"SCADA+APS+QMS 一套后台管到底"的场景——这也是我做三个项目的实际打法：**一套认证、一套用户、一套菜单权限，三个模块的路由挂在一起**。

两条路的取舍：

| 维度 | 独立服务 | 子模块集成 |
|------|---------|-----------|
| 部署复杂度 | 高（多一个进程、多一套配置） | 低（一个进程） |
| 故障隔离 | 好（QMS 崩不影响别模块） | 差（一起崩） |
| 认证/权限 | 各自维护 | 一套共享 |
| 扩展独立 | 好（单独升版本、单独扩容） | 差（一起升） |
| 适用 | 大厂、模块独立团队 | 中小厂、单团队一栈到底 |

中小工厂选**路径 B**——运维简单是第一优先。等哪天 QMS 的负载真的重到需要独立扩容（比如追溯查询压力大），再拆成路径 A 也不迟。**先集成、后拆分**，是"运维得动"原则的又一次体现。

不管哪条路，**建表都要先跑 `qms-init.sql`**：6 张表的 DDL + 一条最小种子数据（第 1 章的原料批 → 成品批谱系 + 检验单 + 控制图子组）。README 里给的是 `psql -d your_db -f yudao-module-qms/src/main/resources/sql/qms-init.sql`。

这块有个**和 APS/blog-api 不同的选择**要交代：QMS 独立运行时用**一次性 SQL 脚本手工建表**，而不是 Flyway 版本化迁移。为什么？因为 **QMS 的表结构是"业务建模的产物"而不是"需要随版本演进的 schema"**——6 张表相对稳定，种子数据是给 Demo 用的。而 blog-api 那种"高频改表、多人协作"的场景才需要 Flyway 的版本管控。不过一旦路径 B 集成进一个成熟工程，**建表就该交给工程的 Flyway**——把 `qms-init.sql` 改写成 `V{n}__qms_init.sql` 放进 `db/migration/`，纳入统一迁移。**独走用手工脚本，集成走 Flyway**，按场景选工具。

把一套 QMS 从零部署起来，动作其实就四步，我列出来给现场的运维照着做：

1. **建库建表**：在 PostgreSQL 里建库（或复用已有的 `blog` 库），`psql -f qms-init.sql` 跑建表 + 种子数据。跑完 `SELECT count(*) FROM qms_batch` 能查到 2 条，就说明种子进来了。
2. **配环境变量**：在部署环境注入 `DB_HOST / DB_PORT / DB_NAME / DB_USER / DB_PASSWORD` 五个变量（数据库连接）和可选的 `QMS_PORT`。**绝不在部署脚本里明文写库密码**，用密钥管理或环境注入。
3. **启动服务**：`java -jar yudao-module-qms.jar`（独立服务）或把模块打进统一的 yudao 工程一起起（集成）。看日志出现"Started"且无 `NoSuchBean`，说明配置类的包扫描/Mapper 扫描都对了。
4. **冒烟验证**：按 README 那五条接口各打一发——`GET /sampling/plan?lotSize=500&aqlLevel=2.5`（抽样方案）、`POST /inspection-order/submit?id=1`（提交检验）、`GET /trace/forward?batchId=1`（正向追溯）、`GET /trace/backward?batchId=2`（反向追溯）、`GET /spc/chart?productCode=P-1002&characteristicCode=外径`（控制图）。**五个接口全返回正常，才算"装好了"**。

这四步看着简单，但**每一步漏了都会表现为"服务起不来"或"接口 500"**——而根因往往在环境变量没注入、包扫描配错、建表脚本没跑这三处之一。一份写清的部署步骤，比事后排查省几个小时。

## 六、边界与踩坑

**坑一：默认密码的"半信半疑"。** 配置里那个默认密码，写的时候要想清"它到底给谁用"。本地开发无害，但**如果部署时忘了注入生产密码、又碰巧连到了本地的同名库**，就会用默认值跑——这是隐患。商用部署清单里必须有一项"确认生产密码由 env 注入、且默认值不会被生产环境命中"。

**坑二：`scanBasePackages` 漏了会静默失效。** 组件扫描范围错，**不会报错、只会"Bean 找不到"**（注入时报 `NoSuchBeanDefinitionException`），排查起来绕。记住"启动类所在包决定扫描范围，模块根包要靠 `scanBasePackages` 上提"这条规则，能省很多时间。

**坑三：`@MapperScan` 路径写错 = Mapper 全失效。** 和上一条类似，`dal.mysql` 写成别的包名，所有 Mapper 都不会生成代理，启动时一排 `NoSuchBeanDefinition`。**路径字符串对不上是纯手误**，最好用 IDE 跳转确认。

**坑四：端口暴露没有鉴权。** 独立服务跑时，8092 端口默认监听 `0.0.0.0`,如果防火墙没拦，任何人都能直接打接口。**要么只监听内网/本机、要么走网关**。安全配置不在这个 yaml 里，但部署时必须处理——这是"代码能跑"和"能上生产"之间的差距。

**坑五：手工建表脚本没有幂等性。** `qms-init.sql` 里是 `CREATE TABLE`（非 `IF NOT EXISTS`）+ `INSERT`，**重复跑会报错或插重复数据**。集成到 Flyway 后由 Flyway 的版本表保证只跑一次；独立跑时要小心别跑两遍。

**坑六：种子数据混进生产库。** `qms-init.sql` 末尾带着两条批次、一条链路、一张检验单、一个 SPC 子组——这是给 Demo 用的**示例数据**。**上线时如果照着脚本全跑进生产库，客户会看到"张三""李四"这些假数据**。正确做法是把 DDL 和 DEMO 数据**拆成两个脚本**：生产只跑建表，示例数据只在测试环境跑。这个坑不致命但很尴尬，我在清单里单列了出来。

**坑七：集成时忘了给菜单/权限授权。** 走路径 B 集成进 yudao 时，`/api/admin/qms/**` 的接口默认是"未授权"的——需要在 yudao 的菜单/权限体系里**建 QMS 的菜单并授权给角色**，否则登录后台看不到任何 QMS 页面。**代码能跑、但界面是空的**，也是集成时最常见的"看起来不对"。

## 七、商用化检查清单（配置部署版）

- 生产环境的 `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` 都通过 env 注入了吗？默认值不会被生产命中吗？
- `QMS_PORT` 与其他模块端口、系统端口无冲突吗？
- `scanBasePackages` 和 `@MapperScan` 路径与模块包结构一致吗？启动无 `NoSuchBean` 报错吗？
- 独立服务的端口做了内网隔离/网关前置吗？
- 建表脚本是否幂等？集成场景是否已改用 Flyway 版本化迁移？
- DDL 与 DEMO 种子数据是否已拆分？生产库会跑进"张三/李四"假数据吗？
- 集成部署时 QMS 菜单是否已建并授权给角色？接口能通但界面空白是常见问题。
- 三个模块（SCADA/APS/QMS）选独立还是集成部署？故障隔离与运维成本评估过了吗？
- 多租户拦截器和软删除在 QMS 表上生效了吗？（`tenant_id`/`deleted` 字段是否被自动注入）
