# 不合格品处置——缺陷代码、MRB 与处置规则引擎

## 一、场景：判了不合格，然后呢

上一章 SPC 预警"过程在漂"，检验单判"这次不合格"。但王主任问了一个最现实的问题："**判了不合格，这批货堆在车间，到底怎么办？**"这不是一个技术问题，是一个**决策问题**，而且是质量体系里最容易出事的地方。

我见过车间里两种极端的处理方式，都不对。**一种是一律报废**——只要判不合格，整批拉去粉碎，图省事、图干净，但成本烧得天怒人怨，明明只是外观有毛刺、性能完全达标的产品，也一起报废了。**另一种是一律"特采放行"**——不合格也照发货，反正客户不知道，赌一把。这两种都是"拍脑袋处置"，没有规则、没有记录、没有责任。

正确的做法是**分类处置**：这个缺陷有多严重？坏在哪？是谁的责任？——按这三个问题的答案，选一种处置方式，而且**选的过程要有据可查、要有人签核**。这就是这一章的主题：**缺陷记录（记录坏在哪、多严重）+ 处置规则引擎（系统给建议）+ MRB 物料评审（人做终审）**。

## 二、缺陷模型：代码、严重度、类别，三个字段定方向

处置的前提是"把缺陷描述清楚"。`QmsDefectDO` 这张表用几个字段把一条缺陷刻画到位：

```java
// dal/dataobject/QmsDefectDO.java
/**
 * QMS 缺陷记录。一次检验中发现的具体缺陷，含严重度、数量、责任工序与处置方式。
 *
 * 处置方式 disposition 为 NULL 表示尚未处置；submitInspection 判定不合格时，
 * 会调用 DispositionRuleEngine 按严重度给出建议处置并回填到未处置的缺陷上。
 */
private String  defectCode;         // 缺陷编码，如 DEF-001
private String  defectName;         // 缺陷名称，如 "毛刺"
private String  defectCategory;     // 缺陷类别，如 "外观" / "尺寸" / "性能"
private Integer severity;           // 1=致命 2=严重 3=轻微
private Integer quantity;           // 缺陷数量
private Integer disposition;        // 1=返工 2=返修 3=让步接收 4=报废 5=退货；NULL=未处置
private String  responsibleProcess; // 责任工序
private String  imageUrl;           // 缺陷图片地址
```

六个字段里，**决定处置方向的是三个**：

**`defectCode` + `defectName`**——缺陷的"身份"。`DEF-001 毛刺`、`DEF-002 缩水`、`DEF-003 尺寸偏大`。为什么要一个**编码**而不只有名称？因为名称是给人看的、会变（"毛刺"有人写"飞边"、有人写"披锋"，同一个东西三种叫法），而编码是给系统统计用的、唯一且稳定。有了编码，才能做"哪个缺陷最高发"的帕累托图，才能跨批次统计同一个缺陷的趋势。**名称求懂，编码求准**，和检验项里"文本标准值 + 数值上下限"是同一种"双轨"思路。

**`defectCategory`（缺陷类别）**——外观 / 尺寸 / 性能。这个字段看着普通，其实是**规则引擎的关键输入**：同样一个"严重"级缺陷，如果是"尺寸"类，可能磨一磨就能修复（返修）；如果是"性能"类，往往修不了（返工甚至报废）。类别是"缺陷能不能通过简单加工挽回"的重要线索。

```java
// enums/QmsDefectSeverity.java
/**
 * 缺陷严重度。严重度直接决定不合格品处置规则的建议方向（致命→报废/退货，严重→返工/返修，轻微→让步接收）。
 */
@Getter
@AllArgsConstructor
public enum QmsDefectSeverity {

    CRITICAL(1, "致命"),
    MAJOR(2, "严重"),
    MINOR(3, "轻微");

    private final Integer code;
    private final String name;
}
```

**`severity`（严重度）** 是三个里最重要的。它分三级：**致命（CRITICAL）**——涉及安全、功能、法规，绝不能流出去（如电器绝缘不合格、药品成分错误）；**严重（MAJOR）**——影响使用但可挽回或客户会不满（如尺寸超差、装配不顺畅）；**轻微（MINOR）**——不影响功能，只是外观瑕疵（如轻微划痕、小毛刺）。严重度**直接决定处置方向的松紧**，是规则引擎的第一个入参。

还有两个字段辅助决策：**`responsibleProcess`（责任工序）** 记录"这个缺陷是哪道工序造成的"，用于责任追溯和整改；**`imageUrl`（缺陷图片）** 存缺陷照片地址——质量追溯里"图"是硬证据，客户投诉时一张现场照片胜过千言。

## 三、五种处置方式

处置方式本身就是一张枚举，五种，覆盖"从全盘接受到彻底退出"的整个谱系：

```java
// enums/QmsDefectDisposition.java
/**
 * 不合格品处置方式。NULL 表示尚未处置。
 */
@Getter
@AllArgsConstructor
public enum QmsDefectDisposition {

    REWORK(1, "返工"),
    REPAIR(2, "返修"),
    CONCESSION(3, "让步接收"),
    SCRAP(4, "报废"),
    RETURN(5, "退货");

    private final Integer code;
    private final String name;
}
```

五种处置要分清楚，因为它们经常被混用：

| 处置 | 含义 | 成本 | 典型场景 |
|------|------|------|---------|
| 返工（REWORK） | 使产品**完全符合**原规格 | 中 | 尺寸超差，重新加工到规格内 |
| 返修（REPAIR） | 使产品**满足预期用途**（但不完全符合原规格） | 中 | 外观修复，功能达标即可 |
| 让步接收（CONCESSION） | **不加工**，客户/内部书面同意放行 | 低（有风险） | 轻微外观瑕疵，客户同意收货 |
| 报废（SCRAP） | 判死，不再使用 | 高 | 功能缺陷无法修复 |
| 退货（RETURN） | 退回供应商 | 转移成本 | 来料缺陷，责任在供应商 |

最容易搞混的是**返工和返修**。标准定义里，**返工是"把产品修到符合原来的规格"**（Rework：make it conform），**返修是"把产品修到能满足使用要求"**（Repair：make it usable），两者差在"是否回到原规格"。外径超了 0.02，磨到 9.95~10.05 里面，是**返工**；外观有个划痕，抛个光让它"看着能用"，但严格说尺寸/表面已不是原始状态，是**返修**。这个区别在质量体系里有法律意义——返修后的产品通常要**标注为返修品**并单独管控，不能当"全新合格品"混出去。当前系统的枚举把两者分开（REWORK=1、REPAIR=2），正是为了保留这个区分。

**让步接收（CONCESSION）** 对应到检验单那一层的 `QmsInspectionResult.CONCESSION(3, "让步接收")`——它是"质量上不合格、业务上放行"的特殊通道，必须有客户或授权人的书面同意。为什么单独开一态而不合并进"合格"？因为**让步接收的产品，其质量状态必须如实留痕**，将来它要是出了问题，追溯链上要能看出"这批货当初就是带着缺陷放行的"，责任归属才清晰。

处置方式的合法性在 Service 层强制校验——`QmsDefectServiceImpl.dispose` 里判断 `disposition >= 1 && disposition <= 5`，非法值直接抛异常：

```java
// service/defect/QmsDefectServiceImpl.java
private boolean isValidDisposition(Integer disposition) {
    return disposition != null && disposition >= 1 && disposition <= 5;
}
```

## 四、处置规则引擎：给"空白缺陷"补建议

核心逻辑在 `DispositionRuleEngine`——一个纯静态工具类，输入"严重度 + 缺陷类别"，输出"建议处置"：

```java
// framework/qms/rule/DispositionRuleEngine.java
@UtilityClass
public class DispositionRuleEngine {

    /** 来源类关键词：命中则判为供应商/来料问题 */
    private static final String[] SUPPLIER_ORIGIN_KEYWORDS = {"来料", "供应商", "原料"};

    /** 可修复类关键词：命中则优先返修而非返工 */
    private static final String[] REPAIRABLE_KEYWORDS = {"尺寸", "外观"};

    /**
     * 给出建议处置方式。
     * @param severity       缺陷严重度
     * @param defectCategory 缺陷类别（如 "外观" / "尺寸" / "性能"）
     * @return 建议处置方式；severity 为 null 时按严重处理（保守）
     */
    public static QmsDefectDisposition suggest(QmsDefectSeverity severity, String defectCategory) {
        if (severity == null) {
            return QmsDefectDisposition.REWORK;
        }
        String category = defectCategory == null ? "" : defectCategory;
        if (severity == QmsDefectSeverity.CRITICAL) {
            return containsAny(category, SUPPLIER_ORIGIN_KEYWORDS)
                    ? QmsDefectDisposition.RETURN
                    : QmsDefectDisposition.SCRAP;
        }
        if (severity == QmsDefectSeverity.MAJOR) {
            return containsAny(category, REPAIRABLE_KEYWORDS)
                    ? QmsDefectDisposition.REPAIR
                    : QmsDefectDisposition.REWORK;
        }
        return QmsDefectDisposition.CONCESSION;
    }

    private static boolean containsAny(String text, String[] keywords) {
        for (String keyword : keywords) {
            if (text.contains(keyword)) {
                return true;
            }
        }
        return false;
    }
}
```

规则其实只有三层，但每层都有讲究：

**致命（CRITICAL）→ 退回供应商或报废。** 如果缺陷类别里带了"来料/供应商/原料"这类**来源关键词**，说明坏的根源在供应商那头，责任可以退货转移；否则是自家生产造成的，只能报废。**"退货"不是降低标准，而是把责任和成本转移回供应商**——这是供应链质量管理的核心动作。注意这里判断的是 `defectCategory` 文本里"含不含"这些词，所以录入缺陷类别时最好把来源信息写进去（如"来料-性能"），规则才命中得准。

**严重（MAJOR）→ 返修或返工。** 缺陷类别命中"尺寸/外观"这类**可修复关键词**，优先**返修**（能修好就用，成本低）；否则**返工**（彻底重做合格）。这条规则背后的直觉是：尺寸、外观问题往往能通过补加工挽回，而性能/结构问题通常得重做。

**轻微（MINOR）→ 让步接收。** 不影响功能的瑕疵，直接放行。这是成本最低的处置，前提是"确实轻微"且"客户能接受"。

**`severity == null` 兜底 → 按"返工"处理。** 这个兜底是**保守**的：严重度不明确时，不敢贸然报废（太浪费）也不敢贸然放行（太危险），取中间值的"返工/返修"最稳妥。这是我在设计时特意选的"最不坏"默认。

## 五、为什么只给建议：MRB 物料评审

看完整段代码，会发现一个刻意的设计：**类名叫 `RuleEngine`，方法叫 `suggest`（建议），不叫 `decide`（裁决）**。这个措辞不是随手起的，是整个质量处置的哲学边界——**系统只给建议，最终处置必须经 MRB（Material Review Board，物料评审）由授权人签核。**

代码注释里写得很清楚：

> MRB（Material Review Board，物料评审）：本引擎只做"系统建议"，不做最终裁决。致命缺陷的报废/退货、以及让步接收都必须经 MRB 会议评审后由授权人签核，系统建议仅作为 MRB 决策的输入。商用实现需把签核结果与建议做差异审计。

为什么不让系统"自动定处置"？三个理由：

**其一，责任在人在组织，不在算法。** 报废一批货、退货给供应商、让步接收发货，这三个动作都涉及**真金白银和客户关系**。出了质量事故追责时，一句"系统自动定的"是站不住的——必须有**具体的人签的字**。系统可以加速决策、可以给建议、可以记流水，但**不能替人担责**。

**其二，规则覆盖不了真实世界的边缘情况。** "致命 + 来料 → 退货"这条规则在 90% 的情况下对，但可能这次来料虽然致命、却是我们自己的返工料混进去的，退货就找错对象了。**真实缺陷的成因千变万化，规则只能给一个起点，最终判断需要一个拿着全部信息的人**。

**其三，MRB 是质量体系的法定程序。** 在 ISO 9001、IATF 16949 这些体系里，不合格品的最终处置本来就规定要经过评审。系统如果绕过 MRB 直接自动处置，等于把**体系合规性**给破坏了——客户审计时这一条就是不符合项。

所以正确的分工是：**系统把"规则的机械建议"作为 MRB 的输入**，MRB 拿着建议（可能同意、可能否决）开会评审，最后由授权人签核。这也是第 5 章 `submitInspection` 第三步的设计逻辑——它只对 `disposition == null`（**还没处置**）的缺陷**回填建议**，已经人工处置过的一律不覆盖。**系统建议是"填空"，不是"改卷"**。

## 六、一条缺陷的全链路：从录入到处置到追溯

把前面几节串起来看，一条缺陷在系统里的完整生命周期是这样的四步：

**第一步：录入缺陷（disposition 为空）。** 检验员在检验单下新建缺陷记录，填 `defectCode / defectName / defectCategory / severity / quantity / responsibleProcess`（可选 `imageUrl`）。此刻 `disposition` 故意留空——**"还没处置"是一个合法且必要的状态**，因为它要等判定、甚至等 MRB。

```java
// service/defect/QmsDefectServiceImpl.java —— createDefect 节选
QmsDefectDO defect = new QmsDefectDO();
defect.setInspectionOrderId(createReqVO.inspectionOrderId());
defect.setDefectCode(createReqVO.defectCode());
defect.setDefectName(createReqVO.defectName());
defect.setDefectCategory(createReqVO.defectCategory());
defect.setSeverity(createReqVO.severity());
defect.setQuantity(createReqVO.quantity());
defect.setDisposition(createReqVO.disposition());   // 通常为 null，待后续处置
defect.setResponsibleProcess(createReqVO.responsibleProcess());
defect.setImageUrl(createReqVO.imageUrl());
defectMapper.insert(defect);
```

**第二步：提交检验，系统回填建议。** 检验单判不合格时，`submitInspection` 第三步对**所有 `disposition == null` 的缺陷**逐条调 `DispositionRuleEngine.suggest`，把建议值写进 `disposition`。这一步是"系统替 MRB 先把草稿拟好"。

**第三步：MRB 评审，人工终审。** 拿着系统建议，MRB 开会评审——同意就直接用（`dispose` 再写一遍同值），不同意就改成人工决定的处置方式。`dispose(defectId, disposition)` 是"人工拍板"的唯一入口，它校验 1~5 的合法性，然后覆盖到 `disposition` 上。**建议和终审值可能不一致，这个差异正是商用审计要记录的东西**。

**第四步：处置结果接回追溯。** 缺陷挂在检验单下，检验单挂着 `batch_id`，而批次又是第 4 章谱系图的节点——所以一条"致命缺陷判退货"的记录，是能顺着链路往上往下走的：往上，查这批料是从哪个供应商来的（反向追溯）；往下，查用了这批料的成品流向了哪些客户（正向追溯）。**处置不是一个孤立的勾选，它是谱系图上的一个坐标点**：知道了"哪个缺陷、多严重、怎么处置"，再叠加"这个缺陷在谱系的哪个位置"，就能算出"影响面有多大、要不要发起召回"。这就是为什么第 1 章那纸投诉能一键回答——因为缺陷、检验、批次、谱系，在数据模型上是**连通的**，不是四张互不相干的表。

## 七、边界与踩坑

**坑一：关键词匹配太脆。** `containsAny` 靠字符串里"含不含某个词"判断，很脆——"供应商"这个词只要缺陷类别里带了就命中，但可能只是备注里顺带一提。这块的鲁棒性依赖**录入规范**（缺陷类别要按固定词表填），商用应改成**缺陷代码映射**（维护一张"代码 → 是否来料来源"的字典表），而不是文本匹配。

**坑二：只按严重度 + 类别，没看数量。** 一个人数出来的 1 个轻微缺陷和 50 个轻微缺陷，严重度都是 MINOR，建议都"让步接收"。但**批量性缺陷哪怕轻微，也可能是系统性问题**，不该一律放行。规则引擎应该考虑 `quantity` 阈值（如"轻微但数量 > N 则升级为返工"）——当前没做，是一个明确的短板。

**坑三：`dispose` 只校验范围不校验状态流转。** 处置方式只能设 1~5，但**能不能从"退货"改成"报废"、能不能在已出货后再改处置**，当前没校验。真实体系里处置是"一旦签核就锁定"的，要改需走**变更流程**。当前实现允许任意改，商用要加状态机。

**坑四：处置没有和批次状态联动。** 一条缺陷判"报废"，按理相关的批次数量要扣减、要做报废出账。当前缺陷处置和批次是"两张皮"，只有 `submitInspection` 那一下联动过批次状态。**处置结果对库存/成本的反哺**是商用必须补的一环。

## 八、商用化检查清单（处置版）

- 缺陷类别是否有固定词表？关键词匹配依赖录入规范，否则规则命中率不稳。
- 是否考虑缺陷数量阈值？批量性轻微缺陷需升级处置。
- 处置是否需要状态机（签核后锁定、变更需审批）？当前可任意改。
- MRB 评审是否有独立的留痕表？建议值与终审值的差异要可审计。
- 处置结果是否联动批次数量/库存/成本？当前是两张皮。
- 让步接收是否强制客户书面同意？这是合规红线。
- 返修品是否单独标注管控？返修品不能当全新合格品混出。

## 九、下一章预告：8D 报告闭环与供应商质量协同

处置解决了"这批货怎么办"，但主机厂那纸投诉要的是一份**8D 报告**——八个步骤，从成立小组、描述问题，到临时措施、找根因、定永久措施、实施、预防再发、团队表彰。这是**从"处理一批货"到"防止同类问题再发生"**的跃迁，也是质量体系里"治本"的仪式化流程。

下一章讲 **8D 报告闭环与供应商质量协同**——8D 八个步骤分别需要系统里的哪些数据支撑、现有的缺陷/追溯/MRB 数据怎么喂进 8D 的 D1~D8、以及为了真正闭环需要补的扩展表（`qms_8d_report`、`qms_capa_action` 之类）。同时讲**供应商质量协同**：来料检验（IQC）发现的问题怎么变成对供应商的退货单和绩效扣分、同一个供应商的问题怎么在系统里积累成"供应商质量档案"。这是承接第 1 章那纸投诉的收官章——**投诉 → 8D → 供应商整改 → 体系预防**。
