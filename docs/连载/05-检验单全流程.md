# 检验单全流程——IQC/IPQC/FQC/OQC 与自动判定

## 一、场景：一张检验单从"送检"到"判完"

前面四章把 QMS 的骨架搭起来了——6 张表建好了，AQL 抽样方案引擎能查表给出 (n, Ac, Re)，批次谱系能正反向追溯。但王主任追问了一个更接地气的问题："料送到检验台之后呢？抽多少个、数出来几个不合格、系统怎么判、判完之后批次算不算合格、缺陷怎么办？这一串动作，是纸上一笔一划记，还是系统一个接口走完？"

这串动作就是**检验单的完整生命周期**。在 QMS 里，一次检验活动不是孤立的一个"合格/不合格"勾选框，而是一条三段式的链：**检验单（order）承载这次检验的"批量、抽样方案、最终判定"；检验项（item）是这次检验里一个一个被测的特性（外径、外观、性能）；缺陷（defect）是检验项判不合格后落下来的具体坏点**。三层从上往下，越往下越具体——单是"这次检什么货"，项是"检了哪些点"，缺陷是"坏在哪"。

这一章要讲的就是"这张单怎么走完流程"：四种检验类型分别盯哪一段、三层结构为什么不能压扁、以及最关键的 `submitInspection()`——它怎么把一堆检验项的不合格数汇总成一次判定，再顺手联动批次状态、回填缺陷处置建议。这是把前四章的表和引擎真正串起来的一章。

## 二、四种检验类型：四个关卡，各盯一段

质量检验在制造业里有四个世界通用的缩写：IQC、IPQC、FQC、OQC。它们不是四个并行的"检验方式"，而是**按检验发生在生产流程的哪个位置**来划分的四个关卡，一个物料从进厂到出厂，要依次过这四道门。

```java
// enums/QmsInspectionType.java
/**
 * 检验类型：按检验发生在生产流程中的位置划分。
 */
@Getter
@AllArgsConstructor
public enum QmsInspectionType {

    IQC(1, "来料检验"),
    IPQC(2, "过程检验"),
    FQC(3, "成品检验"),
    OQC(4, "出货检验");

    private final Integer code;
    private final String name;
}
```

| 类型 | 全称 | 位置 | 盯什么 | 不合格的典型后果 |
|------|------|------|--------|----------------|
| IQC | Incoming Quality Control | 物料入厂 | 供应商送来的原料/外购件 | 退货给供应商、批次冻结 |
| IPQC | In-Process Quality Control | 生产过程中 | 在制品、半成品 | 停线返工、责任工序追溯 |
| FQC | Final Quality Control | 成品完工 | 最终成品 | 整批不合格、不放行 |
| OQC | Outgoing Quality Control | 出货前 | 待出货的成品批 | 拦在厂内、不发货 |

这四个关卡的价值，是把"质量成本"层层递减地拦下来。**IQC 拦住的坏料，代价是退货一批原料；IPQC 拦住的坏料，代价是返工几个在制品；一旦漏到 FQC，代价是整批成品报废；再漏到 OQC 或者客户手里，代价就变成客诉、索赔、丢订单**。质量界有个形象的说法叫"1-10-100 法则"：问题在生产线上花 1 块钱能解决，到成品阶段要 10 块，到客户手里要 100 块。四个检验点，就是三道拦截网，越早拦越省。

在我们的系统里，`QmsInspectionType` 就存在 `qms_inspection_order.inspection_type` 这一列里，默认值是 2（IPQC 过程检验）。为什么默认过程检验？因为中小工厂最常做的、最频繁的就是过程抽检——来料和出货的检验频次低（来料按供应商批次、出货按客户订单），过程检验是天天在做的。种子数据里那张检验单 `QMS-20261013-001` 就是一张 `inspection_type = 2` 的 IPQC 单。

这里有个容易混淆的边界要说清：**检验类型和批次状态是两回事**。`inspection_type` 回答"这是哪道关卡的检验"，`QmsBatchStatus` 回答"这个批次现在处于什么状态"。一张 IPQC 单可以合格也可以不合格，合格则批次变"合格"，不合格则批次变"不合格"——类型是"检什么"，状态是"检完的结果"，两个维度正交。

## 三、三层结构：单 → 项 → 缺陷，为什么不能压扁

一次检验的数据，落在三张表上：`qms_inspection_order`、`qms_inspection_item`、`qms_defect`。上层的检验单通过 `inspection_order_id` 挂住下层的检验项和缺陷。为什么不把检验项直接塞进检验单的字段里？

因为**一次检验测的是"多个特性"，每个特性各有标准、上下限、实测值**。一个注塑外壳的 IPQC 单，可能要检外径（10±0.05）、壁厚、外观（无毛刺）、装配间隙四个特性。如果压进检验单，就得给检验单加 `dim1_value, dim2_value, thickness_value, ...` 一长串列——产品一换，列全废。用子表 `qms_inspection_item` 一列一行地存，**特性数量可多可少、可增可减**，这就是一对多子表的标准价值。

```java
// dal/dataobject/QmsInspectionItemDO.java（字段节选）
private Long inspectionOrderId;   // 所属检验单
private String itemCode;         // 检验项编码，如 DIM-01
private String itemName;         // 检验项名称，如 "外径"
private String standardValue;    // 标准值（文本描述，如 "10±0.05"）
private BigDecimal upperLimit;   // 规格上限
private BigDecimal lowerLimit;   // 规格下限
private BigDecimal actualValue;  // 实测值
private Integer itemResult;      // 1=合格 2=不合格
```

第 2 章讲过 `standard_value`（文本 "10±0.05"）和 `upper_limit/lower_limit`（数值）并存的原因：**文本给人看，数值给机器判**。检验台的操作员看到的是行业写法"10±0.05"，系统做超差判定、拿去做 SPC 控制图时要的是能比大小的 `BigDecimal`。再看种子数据里那张单的两个检验项就很有代表性：

```sql
INSERT INTO qms_inspection_item (..., item_code, item_name, standard_value,
                                 upper_limit, lower_limit, actual_value, unit, item_result) VALUES
(0, 1, 'DIM-01', '外径', '10±0.05', 10.05, 9.95, 10.01, 'mm', 1),
(0, 1, 'APP-01', '外观', '无毛刺', NULL, NULL, NULL, NULL, 2);
```

第一行是**计量型**检验项——外径 10.01，落在 9.95~10.05 里，判合格（`item_result = 1`）。第二行是**计数型**检验项——外观"无毛刺"，这种标准没法量化，`upper/lower/actual` 全空，靠人眼判定，判了不合格（`item_result = 2`）。**计量型和计数型混在一张子表里**，正是 `standard_value` 文本字段和数值字段并存的深层原因：系统必须同时容纳"能用数字卡的"和"只能靠人判的"两类特性。

缺陷表 `qms_defect` 则挂在检验单下（不是挂在检验项下）。为什么？因为**一个缺陷可能跨多个检验项，也可能是一个检验项判坏了之后对"坏成什么样"的更细描述**。外径超差（项判不合格）具体表现可能是"椭圆度超标"或"尺寸偏大"，一条缺陷记录描述的是这个"坏点"。缺陷带严重度、类别、数量、责任工序、图片、处置方式——这些是"处置"章节（第 7 章）的主角，这里先记住它挂在检验单下即可。

## 四、自动判定：submitInspection 完整实现

这是全章的核心。一次检验的检验项录完、缺陷录完后，点"提交检验"，系统做三件事：**汇总不合格数并对照拒收数 Re 判定结果**、**联动批次状态**、**对未处置缺陷回填建议处置**。

```java
// service/inspectionorder/QmsInspectionOrderServiceImpl.java
@Override
public QmsInspectionOrderDO submitInspection(Long id) {
    QmsInspectionOrderDO order = getInspectionOrder(id);

    // 1. 汇总检验项不合格数，对照拒收数 Re 判定
    long failCount = inspectionItemMapper.selectListByOrderId(id).stream()
            .filter(item -> item.getItemResult() != null && item.getItemResult() == ITEM_RESULT_FAIL)
            .count();
    int rejectQty = order.getRejectQty() == null ? 0 : order.getRejectQty();
    boolean pass = failCount < rejectQty;
    int result = pass ? QmsInspectionResult.PASS.getCode() : QmsInspectionResult.FAIL.getCode();

    QmsInspectionOrderDO orderUpdate = new QmsInspectionOrderDO();
    orderUpdate.setId(id);
    orderUpdate.setResult(result);
    orderUpdate.setInspectTime(LocalDateTime.now());
    inspectionOrderMapper.updateById(orderUpdate);

    // 2. 联动批次状态：合格→已合格，不合格→不合格
    if (order.getBatchId() != null) {
        QmsBatchDO batch = batchMapper.selectById(order.getBatchId());
        if (batch != null) {
            QmsBatchDO batchUpdate = new QmsBatchDO();
            batchUpdate.setId(batch.getId());
            batchUpdate.setStatus(pass ? QmsBatchStatus.QUALIFIED.getCode() : QmsBatchStatus.UNQUALIFIED.getCode());
            batchMapper.updateById(batchUpdate);
        }
    }

    // 3. 不合格时，对未处置缺陷按处置规则引擎给出建议（MRB 评审前的系统输入）
    if (!pass) {
        for (QmsDefectDO defect : defectMapper.selectListByOrderId(id)) {
            if (defect.getDisposition() != null) {
                continue;
            }
            QmsDefectDisposition suggest = DispositionRuleEngine.suggest(
                    severityOf(defect.getSeverity()), defect.getDefectCategory());
            QmsDefectDO defectUpdate = new QmsDefectDO();
            defectUpdate.setId(defect.getId());
            defectUpdate.setDisposition(suggest.getCode());
            defectMapper.updateById(defectUpdate);
        }
    }
    return getInspectionOrder(id);
}
```

三步逐个拆。

**第一步的判定线**是这一行：`boolean pass = failCount < rejectQty;`。注意是**严格小于**才合格，不是小于等于。这不是我随手写的，是 AQL 抽样方案的数学定义——抽样方案给出接收数 Ac 和拒收数 Re，且恒有 `Re = Ac + 1`。判定的规则是："**不合格数 ≤ Ac 则接收，不合格数 ≥ Re 则拒收**"。因为 `Re = Ac + 1`，所以"不合格数 ≥ Re"等价于"不合格数 > Ac"，也等价于代码里的"`failCount < rejectQty` 取反"。第 3 章讲的 AQL 引擎负责算出 Ac/Re 并冻结在检验单上，这里就是把检验结果和那个冻结的 Re 比大小。

我特意用 `rejectQty` 而不是 `acceptQty` 来做比较——因为用 Re 时逻辑更"干净"：`failCount < Re` 就是合格，不用写 `failCount <= Ac` 再加一层"等号怎么算"的纠结。种子数据那张单是 n=125、Ac=7、Re=8，那么"不合格数 < 8 即合格"，数出 1 个不合格 → 1 < 8 → 判合格（`result = PASS`）。

**第二步联动批次状态**。检验单上挂着 `batch_id`，判定出结果后把批次状态一起改掉——合格变 `QUALIFIED`（3 = 合格），不合格变 `UNQUALIFIED`（4 = 不合格）。这一步把"质量结果"落到了"批次"这个追溯主体上。为什么要联动？因为批次状态是**下游操作的闸门**：批次"合格"才能放行出货（第 8 章的 `release`），批次"不合格"或"冻结"就卡住。如果检验单判不合格而批次状态还停在"在制"，下一道工序就会误以为它可用——**判定结果必须立刻、自动地流到批次上，不能靠人记得去改**。

```java
// enums/QmsBatchStatus.java
/**
 * 批次/序列号状态。批次是追溯的主体，状态随检验结果与放行/冻结操作流转。
 */
@Getter
@AllArgsConstructor
public enum QmsBatchStatus {

    IN_PROCESS(1, "在制"),
    PENDING(2, "待检"),
    QUALIFIED(3, "合格"),
    UNQUALIFIED(4, "不合格"),
    SHIPPED(5, "已出货"),
    FROZEN(6, "冻结");

    private final Integer code;
    private final String name;
}
```

**第三步回填缺陷处置建议**。判定不合格后，遍历这张单下的缺陷，**对还没处置（`disposition == null`）的**调用 `DispositionRuleEngine.suggest` 给出建议处置并回填。注意 `if (defect.getDisposition() != null) continue;`——**已经人工处置过的不覆盖**。这条 `continue` 是关键：现场质检员可能已经手工填过处置方式（比如他判断这个缺陷虽然轻微但必须返工），系统不能拿"规则引擎的机械建议"去覆盖人工决策。规则引擎只给**空白缺陷**补建议，已经拍过板的一律尊重。

到这里，检验结果和两次枚举也要摆齐：

```java
// enums/QmsInspectionResult.java
public enum QmsInspectionResult {
    PENDING(0, "待检"),
    PASS(1, "合格"),
    FAIL(2, "不合格"),
    CONCESSION(3, "让步接收");
}
```

注意 `CONCESSION`（让步接收）——判定"不合格"后，**不是只有"报废"一条路**。如果缺陷轻微、客户书面同意、或经 MRB 评审认为可以放行，这批货可以"让步接收"：质量上它确实不合格，但业务上允许使用。`CONCESSION = 3` 是介于"合格"和"彻底报废"之间的第三态，也是质量管理里真实存在的第三种结果。整个检验单的结果字段因此有四种取值：0 待检、1 合格、2 不合格、3 让步接收。

## 五、这几个枚举，串起了整个流程

检验单这一路走下来，会牵动四个枚举，它们分别管四个维度，我摆一张表理清：

| 枚举 | 管的维度 | 取值 |
|------|---------|------|
| `QmsInspectionType` | 这是哪道关卡 | IQC(1) / IPQC(2) / FQC(3) / OQC(4) |
| `QmsInspectionResult` | 检验单判成什么 | PENDING(0) / PASS(1) / FAIL(2) / CONCESSION(3) |
| `QmsBatchStatus` | 批次现在什么状态 | 在制(1) … 合格(3) / 不合格(4) / 已出货(5) / 冻结(6) |
| `QmsDefectSeverity` | 缺陷有多严重 | CRITICAL(1) / MAJOR(2) / MINOR(3) |

`QmsDefectSeverity` 是第 7 章的引子——`submitInspection` 第三步调 `DispositionRuleEngine.suggest` 时，第一个参数就是它。严重度决定处置方向：致命→报废/退货，严重→返工/返修，轻微→让步接收。这里先埋下伏笔，下一章（不，是第 7 章）展开讲。

```java
// enums/QmsDefectSeverity.java
public enum QmsDefectSeverity {
    CRITICAL(1, "致命"),
    MAJOR(2, "严重"),
    MINOR(3, "轻微");
}
```

## 六、边界与踩坑

**坑一：`failCount` 用 long 还是 int。** `stream().count()` 返回的是 long，和 `rejectQty`（int）比较时 Java 会自动提升 int 为 long，没毛病。但要是漏写了 `int rejectQty = order.getRejectQty() == null ? 0 : order.getRejectQty();`，直接拿 `order.getRejectQty()`（可能是 null）去比较，就是 NPE。**抽样方案是可选填的**——一张检验单可能还没定抽样方案就被提交了，所以 Re 必须兜一个默认 0。Re=0 意味着"`failCount < 0`"永远为 false → 永远判不合格，这其实是一个合理的安全默认：**没有抽样方案就不该判合格**。

**坑二：计数型检验项怎么"判不合格"。** 外观这种靠人眼判的项，`item_result` 由检验员直接置 1 或 2，系统不去算超差。这带来一个隐患：**人工判的项也可能漏判、误判**，系统只做汇总不做事实验证。商用实现要加"判定依据"字段（照片、记录人）留痕。当前 MVP 信任检验员的判定，把"项级判定"和"单级汇总"分层：人判项，系统判单。

**坑三：批次状态联动是单向的。** `submitInspection` 会把批次打成"合格"或"不合格"，但反过来——**如果同一批次后续又做了一次复检**，两次判定谁说了算？当前实现是"后一次覆盖前一次"。严格的质量体系里，复检应该有优先级（如"合格需全项合格，任一次不合格则不合格"），商用需要把判定加一层"合并策略"。MVP 先用最朴素的"最后一次判定为准"。

**坑四：`submitInspection` 没有事务注解。** 它一连动了三张表（检验单、批次、缺陷），如果第三步回填缺陷中途抛异常，前两步已经提交了，数据就不一致了。这是一个**必须在商用前补 `@Transactional` 的点**——我在检查清单里也标了出来。

## 七、商用化检查清单（检验流程版）

- `submitInspection` 加了 `@Transactional` 吗？它跨三张表写入，必须原子。
- `rejectQty` 为空时的默认 0 是否安全？当前语义是"无方案即不合格"，确认符合业务预期。
- 复检场景的判定合并策略是什么？当前"最后一次为准"，商用需定义优先级。
- 计数型检验项的判定留痕了吗？人工判定是否记录了依据（图片/备注/判定人）？
- 让步接收（CONCESSION）走 MRB 审批了吗？它是"不合格但放行"，必须有签核留痕。
- 检验单判不合格后，是否需要自动冻结批次而非仅置"不合格"？两者对下游的影响不同。

## 八、下一章预告：SPC 统计过程控制

到这里，检验单的三层结构、四种类型、自动判定三步就讲完了——判定是"事后把关"：抽完样、数完不合格、判一个合格或不合格。但王主任还有一张牌没打：**尺寸在慢慢漂、刀具在慢慢磨，能不能在批量超差之前就看出苗头？**

事后把关只能拦住"已经坏了的"，而 SPC（统计过程控制）要拦的是"**正在往坏的方向走、还没坏透的**"。下一章讲 SPC——X-Bar/R 控制图怎么用 A2/D4/D3 系数算出上下控制限，Cpk 怎么刻画过程能力，Western Electric 的 4 条判异规则怎么自动预警"连续 9 点在中心线同侧""连续 6 点持续上升"。`SpcCalculator` 那三个系数数组和 `westernElectricRules` 的完整实现，是下一章的主角。
