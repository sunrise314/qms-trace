# 8D 报告闭环与供应商质量协同

## 一、场景：那纸投诉要的不是"处理"，是"不再发生"

回到第 1 章那纸主机厂投诉。王主任第一次我帮他追溯时，关注的是"这批货用了哪批料、流向了哪些客户"——那是**处理一个具体问题**。但主机厂的回复要求里，还有一条更要命：**提交 8D 报告**。8D 不是"你把这批货处理了就完事"，而是"你要告诉我**为什么会这样、你打算怎么保证下次不再这样**"。前者治标，后者治本。

8D 报告是汽车、电子、医疗这些供应链行业的**通用语言**。主机厂问供应商要恢复质量信任，标准动作就是要一份 8D：八个步骤（Discipline），从组建小组一路到预防再发。**没有 8D，等于没有承认问题、没有整改承诺**——保证金照扣，订单照砍。

这一章分两块。第一块讲 **8D 报告闭环**：八个步骤分别需要系统里的哪些数据、现有 QMS 已经能支撑到哪一步、为了真正闭环还要补哪些扩展表。第二块讲 **供应商质量协同**：来料检验（IQC）发现的问题怎么变成"退货单 + 供应商绩效扣分"，同一个供应商的问题怎么沉淀成"供应商质量档案"，最终反向逼供应商整改。这是承接第 1 章那纸投诉的收官之章——**投诉 → 8D → 供应商整改 → 体系预防**。

## 二、8D 方法论：八个步骤

8D（Eight Disciplines，八项纪律）是福特首创、后来全行业通用的质量问题解决流程。八个步骤名字和动作是固定的：

| 步骤 | 名称 | 核心动作 |
|------|------|---------|
| D1 | 组建团队（Team） | 拉齐跨职能小组：质量、工艺、生产、供应商 |
| D2 | 描述问题（Describe） | 5W2H 把问题钉死：什么货、什么缺陷、何时、何处、多少 |
| D3 | 临时遏制（Containment） | 隔离不良品、圈定受影响批次、通知客户（**召回**） |
| D4 | 根因分析（Root Cause） | 用 5 Why / 鱼骨图找到根本原因，验证 |
| D5 | 永久对策（Corrective Action） | 定并验证纠正措施（改工艺/改模具/改检验） |
| D6 | 实施验证（Implement） | 落地永久对策，确认有效 |
| D7 | 预防再发（Prevent） | 横向展开到相似产品/工序，更新控制计划 |
| D8 | 团队与表彰（Congratulate） | 结案、归档、肯定团队 |

关键要先分清 8D 里一对最容易搞混的动词：**D3 遏制 vs D5 永久对策**。D3 是"**临时止血**"——出事了先隔离、先通知、先别让坏料继续往下走（对应我们第 4 章的**正向追溯/召回**）；D5 是"**根治预防**"——找到根因后改掉产生缺陷的那个系统（改模具、改参数、改检验规则）。**先止血再治病**，这是 8D 的时间顺序：客户等不了你做完根因分析，先给个临时的可接受方案（D3），承诺整改（D5~D7）。

## 三、现有系统能喂给 8D 的，到底有哪些

好消息是：QMS 前面七章攒下的数据，**天然就是 8D 的原材料**。我不是为了做 8D 才设计这些表，而是这些表本身在"描述问题、圈定范围、找根因"上就够专业。对照着看：

| 8D 步骤 | 需要的数据 | 现有系统对应 |
|---------|-----------|-------------|
| D1 组建团队 | 涉及的角色/工序 | `qms_defect.responsible_process`（责任工序） |
| D2 描述问题 | 什么缺陷、多严重、多少 | `qms_defect`（defectCode / severity / quantity / imageUrl） |
| D3 临时遏制 | 受影响批次范围 | `qms_trace_link` + 正反向 BFS（第 4 章） |
| D4 根因分析 | 缺陷集中在哪道工序/哪台机 | 批次 `machine_code` + 缺陷责任工序，跨批次聚合 |
| D5 永久对策 | 处置方式与整改 | `qms_defect.disposition`（第 7 章）+ 人工填 CAPA |
| D6 实施验证 | 整改后是否复发 | SPC 控制图 + 后续检验单合格率（第 5/6 章） |
| D7 预防再发 | 同类缺陷趋势 | 缺陷编码跨批次统计（帕累托） |
| D8 结案 | 归档 | 缺（需要 8D 报告表） |

**D2 描述问题** 直接由 `QmsDefectDO` 支撑。回到第 7 章那张缺陷表——`defectCode`、`defectName`、`severity`、`quantity`、`imageUrl`，这几个字段拼起来就是 8D D2 要的"5W2H 描述"的一半（什么缺陷、多少、长什么样）：

```java
// dal/dataobject/QmsDefectDO.java —— D2/D4 的数据来源
/** 缺陷编码，如 DEF-001 */           private String defectCode;
/** 缺陷名称，如 "毛刺" */             private String defectName;
/** 缺陷类别，如 "外观" / "尺寸" / "性能" */ private String defectCategory;
/** 1=致命 2=严重 3=轻微 */            private Integer severity;
/** 缺陷数量 */                       private Integer quantity;
/** 责任工序 */                       private String responsibleProcess;
/** 缺陷图片地址 */                   private String imageUrl;
```

**D3 临时遏制** 是现有系统最拿得出手的一步——第 4 章的 `GenealogyGraph` 正反向 BFS 一跑，"问题料流向哪些客户、哪些批次"就出来了。8D 报告里 D3 那一段"受影响范围"，是系统**自动算出来的**，不是人工翻三天纸。

**D4 根因分析** 有一点系统能帮上：把 `responsibleProcess`（责任工序）和批次上的 `machine_code`（机台）、`shift`（班次）一联动，就能看出"这个缺陷是不是集中在 2 号机的夜班"——**数据指方向，人找根因**。系统不做鱼骨图的推理，但能告诉你该从哪个维度查。

拿王主任那纸投诉把 8D 走一遍，数据怎么跟就清楚了：**D2** 从缺陷表读出"P-1002 成品组件、外壳开裂、严重、客户装配后暴露"；**D3** 用 `GET /trace/forward?batchId=1` 一圈，发动机立刻拿到"这批料还流向了 3 个客户、5 个批次"；**D4** 把缺陷的责任工序和批次机台一联，发现开裂集中在"2 号注塑机的夜班批次"；**D5/D6** 定对策（调整 2 号机保压参数 + 增加开模后冷却检查），落地后再跑 SPC 看开裂相关特性的控制图稳不稳；**D7** 把这条对策横向展开到 1、3 号机（相似产品）；**D8** 结案归档。**另一半是"人"**——系统给了 D2 的事实和 D3 的范围，但 D4 的根因得工程师去现场看、D5 的对策得工艺去改、D7 的横向展开得管理者拍板。**系统负责"数据到齐"，人负责"判断与担责"**，这和第 7 章 MRB"系统建议、人工终审"是同一个边界哲学。

## 四、扩展设计：给 8D 补三张表

到 D5 往后，现有的 6 张表就不够了——它们记的是"事实"（缺陷、批次、检验），而 8D 需要记的是"**过程"（团队、根因、措施、验证、结案）**。这是一类新的实体，需要新表。我的扩展设计建议是三张：

```sql
-- 8D 报告主表：一条 8D 对应一个问题（可能关联多条缺陷/多个批次）
CREATE TABLE qms_8d_report (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT       NOT NULL,
    report_no     VARCHAR(64)  NOT NULL,               -- 8D 报告编号，如 8D-20261013-001
    title         VARCHAR(256) NOT NULL,               -- 问题标题
    source        SMALLINT     NOT NULL,               -- 1=客户投诉 2=来料 3=内部 4=过程
    severity      SMALLINT     NOT NULL,               -- 严重度（继承缺陷）
    batch_id      BIGINT,                              -- 关联批次（追溯起点）
    customer_code VARCHAR(64),                         -- 客户/主机厂编码
    status        SMALLINT     NOT NULL DEFAULT 1,     -- 1=开启 2=处理中 3=待验证 4=已关闭
    owner         VARCHAR(64),                         -- 8D 负责人
    due_time      TIMESTAMPTZ,                         -- 客户要求的回复时限
    UNIQUE (tenant_id, report_no, deleted)
);

-- 8D 步进表：报告下的 D1~D8 每一步的内容与签核（一对多）
CREATE TABLE qms_8d_step (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT       NOT NULL,
    report_id     BIGINT       NOT NULL REFERENCES qms_8d_report (id) ON DELETE CASCADE,
    discipline    SMALLINT     NOT NULL,               -- 1~8 对应 D1~D8
    content       TEXT,                                -- 该步骤内容（团队名单/根因/对策...）
    verifier      VARCHAR(64),                         -- 该步签核人
    verify_time   TIMESTAMPTZ,
    UNIQUE (tenant_id, report_id, discipline, deleted)
);

-- CAPA 措施表：纠正/预防措施（D5~D7 落地），可横向展开到多产品
CREATE TABLE qms_capa_action (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT       NOT NULL,
    report_id     BIGINT       REFERENCES qms_8d_report (id) ON DELETE CASCADE,
    action_type   SMALLINT     NOT NULL,               -- 1=纠正 2=预防
    description   VARCHAR(512) NOT NULL,               -- 措施描述
    owner         VARCHAR(64),
    due_time      TIMESTAMPTZ,
    status        SMALLINT     NOT NULL DEFAULT 1,     -- 1=待办 2=进行 3=完成 4=已验证
    effect_check  VARCHAR(512)                         -- 效果验证结论
);
```

三张表的分工很清楚：`qms_8d_report` 是**一份 8D 的户口本**（谁的问题、对哪个客户、什么时限）；`qms_8d_step` 是**八个步骤的流水**（每步的内容和签核）；`qms_capa_action` 是**整改措施的台账**（做了什么、谁做、做完没、效果如何）。**D1~D8 用一张"步进表"+ 一个 `discipline` 列**，而不是建八张表——因为八个步骤结构相同（内容 + 签核人 + 时间），八张表会带来八套 CRUD，一张表加个"是哪一步"的列更省。

注意 `qms_8d_report.batch_id` 那条外键——**8D 报告挂在批次上**，就能在第 4 章的谱系图里定位它的位置，8D 的 D3（遏制范围）直接调用追溯引擎即可，不用另起炉灶。这就是"扩展表和既有模型**挂钩不脱钩**"的价值。

## 五、供应商质量协同：把来料问题变成供应商的账

8D 的另一半价值在**供应商**。主机厂对注塑厂做 8D，注塑厂对它的原料供应商也要做 8D——**链条是往上传的**。这块的入口是 IQC（来料检验）：

```java
// enums/QmsInspectionType.java —— 供应商问题的入口
public enum QmsInspectionType {
    IQC(1, "来料检验"),     // ← 供应商质量协同的入口
    IPQC(2, "过程检验"),
    FQC(3, "成品检验"),
    OQC(4, "出货检验");
}
```

来料检验（IQC）判不合格，走的正是第 7 章那套链路：缺陷判"致命"、类别带"来料/供应商/原料"关键词，`DispositionRuleEngine.suggest` 给出**退货（RETURN）**的建议：

```java
// framework/qms/rule/DispositionRuleEngine.java —— 供应商问题的处置分支
private static final String[] SUPPLIER_ORIGIN_KEYWORDS = {"来料", "供应商", "原料"};
// ...
if (severity == QmsDefectSeverity.CRITICAL) {
    return containsAny(category, SUPPLIER_ORIGIN_KEYWORDS)
            ? QmsDefectDisposition.RETURN    // 来料来源 → 退货，责任转移回供应商
            : QmsDefectDisposition.SCRAP;    // 自家生产 → 报废
}
```

"退货"这个动作，落到**批次状态**上就是"冻结"——不合格的来料批次不能再被投料使用：

```java
// enums/QmsBatchStatus.java —— 来料批次不合格后应冻结
public enum QmsBatchStatus {
    IN_PROCESS(1, "在制"),
    PENDING(2, "待检"),
    QUALIFIED(3, "合格"),
    UNQUALIFIED(4, "不合格"),
    SHIPPED(5, "已出货"),
    FROZEN(6, "冻结");     // ← 来料退货/待处理的批次状态
}
```

**供应商质量协同**要做的，是把这个"单次退货"上升成"供应商绩效档案"。同一个供应商，系统里积累的每一次 IQC 退货、每一个致命缺陷，都挂在**供应商编码**上。用 `supplier + defectCode` 一聚合，就能算出：

- **退货率**：某供应商某一年的来料批次里，被判退货的比例——超过阈值（如 5%）就触发**降级/约谈**；
- **缺陷集中度**：某供应商的缺陷是不是集中在某一类（如总是"尺寸"）——说明它某道工序有系统问题，8D 要它整改的就是这道工序；
- **复现率**：同一个缺陷整改后**又出现**——这是最严重的信号，说明它的 8D 只是"纸面整改"，要升级到**暂停供货**。

架构上，这些指标不需要新建"供应商表"——用现有 `qms_defect`（缺陷） + `qms_batch.attributes`（JSONB 里那个 `supplier` 字段，第 2 章种子数据里原料批就存了 `{"supplier":"X塑胶厂"}`） + `qms_inspection_order`（IQC 单）**聚合出来**就行。**供应商档案是"算"出来的视图，不是"录"进去的表**——这也符合我们"表少、算多"的整体风格。

这么做还有一个附加价值：**供应商的整改效果，可以用数据验证**。供应商说"我已经改进了"，你不必只听他嘴上说——把整改前后的退货率、缺陷集中度一对比，是不是真改好了，数据说了算。这是"用系统把供应商的承诺变成可度量的事实"。对供应商而言，这也公平：做得好，档案里退货率低，订单给你；做得差，复现率高，降级限量。**质量协同不是靠人情，是靠数据说话的长期博弈。**

## 六、边界与踩坑

**坑一：8D 的步骤签核不能退化成"填个表"。** `qms_8d_step` 只是一个容器，真正的价值在于"**哪一步做了、谁签的字、什么时间**"。如果只做了建表却没有**流程约束**（比如 D4 没签核就不许进 D5），8D 就退化成了"事后补文档"，失去了"过程留痕"的意义。商用要把八个步骤做成**顺序推进的状态机**。

**坑二：D3 遏制和 D5 对策混在一个字段。** 如果只把 8D 内容写成一坨文本，D3 的"临时措施"和 D5 的"永久对策"就分不清了。**临时措施是"先扛住"，永久对策是"根治"**，两者必须分字段、分责任人、分时限（D3 往往要求 24 小时，D5 可以几周）。步进表按 `discipline` 分开存，就是为了逼着填的人分清这两类。

**坑三：追溯的"遏制范围"可能漏。** D3 的召回范围靠第 4 章的 BFS 算，但 BFS 依赖**边数据的完整性**——如果车间有些投料没录链路边，追出来的范围就是漏的。8D 里 D3 是最要命的（漏一个客户就是一次事故），所以在商用清单里必须查"链路边覆盖率"。

**坑四：供应商数据散在 JSONB 里。** 第 2 章把 `supplier` 塞进了 `qms_batch.attributes`（JSONB），做单批查询没问题，但**按供应商做年度聚合**要用 JSONB 提取函数（`attributes->>'supplier'`），性能和索引都不如独立的 `supplier_id` 列。商用阶段建议把供应商从 JSONB 提出来，单独建一张 `qms_supplier` 主数据表，批次引用它的 ID。

## 七、商用化检查清单（8D 与供应商版）

- 8D 报告表建了吗？D1~D8 的步骤内容和签核是否留痕？
- 八个步骤是否有序推进的状态机？还是允许"事后补文档"？
- D3 触发时，追溯引擎能否一键算出完整的客户/批次范围？覆盖了多少漏录的边？
- CAPA 措施是否有"效果验证"闭环？整改后是否复现过？
- 供应商退货率/复现率指标算得出来吗？`attributes->>'supplier'` 聚合性能如何？
- 供应商是否已从 JSONB 提升为独立主数据？商用聚合需要索引支持。
- 8D 报告是否与批次、缺陷双向可跳转（从投诉看到 8D、从 8D 回到谱系）？
