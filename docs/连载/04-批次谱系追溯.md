# 批次谱系追溯——正反向 BFS 圈定召回边界

## 一、场景：从"翻三天纸"到"点一下出结果"

第 1 章开头那纸投诉，最难的那个问题是"**同批原料还流向了哪些客户、哪些批次**"。这问题纸质记录基本答不了——因为成品单据上只写"我用了一批料"，但没有地方写"这批料被谁用了"。要正向回答，得把几千张单据全翻一遍，人工建一张倒排索引。

追溯本质上有两个方向，业务话术完全不同：

- **正向追溯（forward）**：从"问题料"出发，问"**我的料去哪了**"。场景是**召回**——某批原料被判定不合格（供应商自曝批量性缺陷、IQC 抽检不合格），必须立刻圈定所有用到它的下游成品批，通知相应客户。答慢了是赔钱，漏了是质量事故。
- **反向追溯（backward）**：从"问题货"出发，问"**问题在哪批料**"。场景是**溯源**——客户投诉某批成品开裂，要定位是哪批原料、哪道工序引入的。答不准，就找不到责任方，赔了钱还不知道找谁。

两个方向，**同一张图的两种走法**——这正是我写 `GenealogyGraph` 时最核心的洞察：正向和反向都是对同一张邻接表的广度优先遍历（BFS），只是遍历方向相反，所以它们可以**共用一个内部实现**。

## 二、为什么不上 Neo4j

"批次谱系是图，那就上图数据库啊"——这是标准直觉。我一开始也这么想，打听了一圈 Neo4j、JanusGraph，最后放弃了。三个理由：

**其一，规模不够。** 注塑厂的批次量级是多少？一个月几千批，一年几万批，全部历史几百万条边。这个规模，一张带索引的邻接表 + Java 内存 BFS，毫秒级就出结果。Neo4j 的杀手场景是"几十亿点、图算法密集"（社交网络、推荐、反洗钱），我们的场景是"几百万边、两跳遍历"，**杀鸡用牛刀**。

**其二，运维成本。** 每多一个数据库，就多一套部署、备份、高可用、监控、调优。厂里已经有一套 Postgres 在跑（SCADA、APS 也用），QMS 的表跟着进去，一套运维体系全覆盖。再引一个 Neo4j，等于给一个中小厂的 IT 加一个完全不熟的组件——**出事没人会修**。

**其三，溯源可解释。** 关系库里的邻接表，每一行边都是明明白白的数据，`EXPLAIN ANALYZE` 一看就走索引。Neo4j 的图查询对工程师是黑盒，出了性能问题很难调。质量追溯这种事，**宁可慢一点也要可解释**。

所以取舍表里那条"邻接边表 + 内存 BFS，无需图数据库"不是偷懒，是**规模决定架构**。这也呼应了 README 的商用检查项："大批量场景改用 PostgreSQL 递归 CTE（`WITH RECURSIVE`）"——真到了几千万边的规模，我们还有一条升级路径，而不是推翻重来。

## 三、邻接表怎么建

BFS 的第一步是"建邻接表"。给定全量边，要为每个"起点批次"列出它的邻居。

```java
// framework/qms/trace/GenealogyGraph.java —— traverse 方法内的邻接表构建
// 构建邻接表：按遍历方向，把每条边的"起点"作为 key
Map<Long, List<TraceLinkVO>> adjacency = new HashMap<>();
for (TraceLinkVO link : links) {
    Long key = forward ? link.fromBatchId() : link.toBatchId();
    if (key == null) {
        continue;
    }
    adjacency.computeIfAbsent(key, k -> new ArrayList<>()).add(link);
}
// 邻居按流转时间升序，保证同一层内"按时间"有序（null 排最后）
adjacency.values().forEach(list -> list.sort(
        Comparator.comparing(TraceLinkVO::linkTime, Comparator.nullsLast(Comparator.naturalOrder()))));
```

关键在那行 `Long key = forward ? link.fromBatchId() : link.toBatchId();`——**正向遍历就把边的 `from` 端当 key，反向遍历就把 `to` 端当 key**。这一行让同一个邻接表结构同时服务两个方向，是整个引擎最省事的设计。

建完还要给邻居排序：按 `linkTime` 升序。为什么？因为追溯结果要给现场看——"这批料先投给了 A 批、后投给了 B 批"才是符合直觉的顺序。`Comparator.nullsLast` 处理了 `linkTime` 为空的情况（排序放最后，不崩）。**同一层内按时间有序**，让追溯报告读起来像一条时间线。

## 四、边与节点的 VO

BFS 走的是图，但给前端要的是"能渲染的箭头和节点"。这里有两个 `record`：

```java
// framework/qms/trace/TraceLinkVO.java
/**
 * 追溯链路 VO——谱系图中的一条边。同时带上首尾批次号，便于前端直接渲染带标签的箭头。
 */
public record TraceLinkVO(
        Long fromBatchId,    // 上游批次 ID
        String fromBatchNo,  // 上游批次号
        Long toBatchId,      // 下游批次 ID
        String toBatchNo,    // 下游批次号
        Integer linkType,    // 关系类型（1=投料 2=拼批 3=分拆 4=装配 5=返工）
        BigDecimal quantity, // 流转数量
        LocalDateTime linkTime // 流转时间
) {
}
```

注意 `TraceLinkVO` 比数据库的 `QmsTraceLinkDO` 多带了 `fromBatchNo` / `toBatchNo` 两个字段。这是刻意的——**DO 里只有 ID，前端渲染箭头时需要"批次号"这个人类可读的标签**。与其让前端拿着 ID 再一个个回查批次号，不如在组装 VO 时一次性补齐（`QmsTraceServiceImpl` 的做法，后面会讲）。这是典型的"**查询时一次多带点、渲染时少跳一次**"。

```java
// framework/qms/trace/BatchNode.java
/**
 * 追溯图中的批次节点。由 QmsBatchDO 映射而来，只保留谱系渲染需要的字段。
 */
public record BatchNode(
        Long id,
        String batchNo,
        String productCode,
        String productName,
        Integer quantity,
        Integer status,
        String machineCode,
        String shift,
        LocalDateTime produceTime
) {
}
```

`BatchNode` 是 `QmsBatchDO` 的"渲染投影"——从 20 多个字段里砍出 9 个（批次号、产品、数量、状态、机台、班次、生产时间等），刚好够在图里画一个节点。**追溯结果不需要知道租户、创建人、备注这些运维字段**，砍掉它们让返回的 JSON 更小、语义更干净。

## 五、核心 BFS 实现

这是全章最重要的一段——`GenealogyGraph.traverse` 的完整实现：

```java
// framework/qms/trace/GenealogyGraph.java
/**
 * 通用 BFS 遍历。forward=true 沿 from→to 方向展开，false 则沿 to→from 方向展开。
 *
 * @param links       全量追溯链路（调用方一次性加载；大批量场景建议改递归 CTE）
 * @param rootBatchId 根批次 ID
 * @param forward     遍历方向
 * @return 有序批次 ID + 最大深度
 */
public static Traversal traverse(List<TraceLinkVO> links, Long rootBatchId, boolean forward) {
    if (rootBatchId == null || links == null || links.isEmpty()) {
        return new Traversal(List.of(), 0);
    }
    // ... 邻接表构建（见上节）...

    List<Long> order = new ArrayList<>();
    Set<Long> visited = new HashSet<>();
    Map<Long, Integer> depthOf = new HashMap<>();
    Deque<Long> queue = new ArrayDeque<>();

    visited.add(rootBatchId);
    depthOf.put(rootBatchId, 0);
    queue.add(rootBatchId);
    int maxDepth = 0;

    while (!queue.isEmpty()) {
        Long current = queue.poll();
        int currentDepth = depthOf.getOrDefault(current, 0);
        for (TraceLinkVO link : adjacency.getOrDefault(current, List.of())) {
            Long next = forward ? link.toBatchId() : link.fromBatchId();
            if (next == null || visited.contains(next)) {
                continue; // 已访问（防环）
            }
            visited.add(next);
            depthOf.put(next, currentDepth + 1);
            maxDepth = Math.max(maxDepth, currentDepth + 1);
            order.add(next);
            queue.add(next);
        }
    }
    return new Traversal(order, maxDepth);
}
```

一个标准 BFS，但对于"质量追溯"这个场景，有四个细节值得单独说：

**细节一：`visited` 集合 = 防环。** 这是最重要的一行。谱系数据是业务录入的，**可能脏**——比如操作员把"返工批"的边录成了一条环（A 返工成 B，B 又返工回 A），或者更隐蔽的"投料 A→B，B 又投给 A"。如果 BFS 不防环，队列会无限增长，直接 OOM。`if (next == null || visited.contains(next)) continue;` 这一句保证每个批次**只入队一次**，图里就算真有环，BFS 也会在第二次遇到同一点时停下。

**细节二：`depthOf` 记录层号。** 根批次深度 0，它的直接邻居深度 1，再下一层 2…… `maxDepth` 是整张子图的最大层数。为什么需要深度？——因为追溯报告要告诉现场"**这批料的直接去向（1 跳）有多少、间接去向（2 跳以上）有多少**"。1 跳是"直接投料"，通常责任清晰；2 跳以上是"下游的下游"，是召回的难点。把深度带回，前端就能按层渲染。

**细节三：`order` 是层序的。** BFS 天然按层展开——先所有深度 1 的，再所有深度 2 的。加上前面邻接表"同一层内按时间排序"，最终 `order` 就是一个"**按层、层内按时间**"的有序批次列表，直接就是追溯报告的阅读顺序。

**细节四：只返回 ID，不带节点数据。** `traverse` 只算"哪些批次 ID 被命中了"，不碰批次详情。节点详情（批次号、产品名）由 Service 层在拿到 ID 集合后一次性回查。**引擎只算图，Service 管取数**——职责分离，引擎可以纯单元测试（给它一堆边和一个根 ID，断言输出 ID 列表）。

`GenealogyGraph` 还包了两个语义化入口 `forward(links, root)` / `backward(links, root)`，它们只是 `traverse(..., true/false).order()` 的薄封装；`traverse` 返回的 `Traversal` 是个 record（`order` 有序 ID 列表 + `depth` 最大层号），根批次不计入 `order`。

## 六、Service 层：把图喂给引擎、把结果组装成报告

引擎只管图，`QmsTraceServiceImpl` 负责"取数 → 喂引擎 → 组装结果"。它的核心流程：

```java
private TraceResult trace(Long batchId, QmsTraceDirection direction, boolean merge) {
    List<QmsTraceLinkDO> linkDOs = traceLinkMapper.selectListAll();

    // 一次性把链路端点 + 根批次对应的批次信息捞回来，既做链路标签，又做节点组装
    Set<Long> endpointIds = new HashSet<>();
    endpointIds.add(batchId);
    for (QmsTraceLinkDO link : linkDOs) {
        if (link.getFromBatchId() != null) endpointIds.add(link.getFromBatchId());
        if (link.getToBatchId() != null) endpointIds.add(link.getToBatchId());
    }
    Map<Long, QmsBatchDO> batchById = new HashMap<>();
    for (QmsBatchDO batch : batchMapper.selectListByIds(endpointIds)) {
        batchById.put(batch.getId(), batch);
    }
    if (!batchById.containsKey(batchId)) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_BATCH_NOT_EXISTS, batchId);
    }

    List<TraceLinkVO> links = new ArrayList<>();
    for (QmsTraceLinkDO link : linkDOs) {
        links.add(toLinkVO(link, batchById));
    }
    // ... BFS + 组装 ...
}
```

这里有三个工程细节：

**其一，批次信息"一次性捞回"。** 先把所有边的两端 ID 收进 `endpointIds`，再 `selectListByIds` 一把查回 `Map<Long, QmsBatchDO>`，而不是在 BFS 里对每个批次单独查——**避免 N+1**。这个 Map 同时干两件事：给 `TraceLinkVO` 补批次号标签，给最终结果组装 `BatchNode`。

**其二，根批次不存在直接抛异常。** `if (!batchById.containsKey(batchId))` 说明根批次没查到，抛 `ERROR_CODE_BATCH_NOT_EXISTS`。追溯必须有一个存在的起点。

**其三，正向/反向/合并三种模式。** `traceReport`（完整报告）走的是 `merge = true` 分支——正反两个方向都跑，`LinkedHashSet` 把两边节点合并去重：

```java
Set<Long> nodeIds = new LinkedHashSet<>();
int depth;
if (merge) {
    GenealogyGraph.Traversal backward = GenealogyGraph.traverse(links, batchId, false);
    GenealogyGraph.Traversal forward = GenealogyGraph.traverse(links, batchId, true);
    nodeIds.addAll(backward.order());
    nodeIds.addAll(forward.order());
    depth = Math.max(backward.depth(), forward.depth());
} else {
    boolean forward = direction == QmsTraceDirection.FORWARD;
    GenealogyGraph.Traversal traversal = GenealogyGraph.traverse(links, batchId, forward);
    nodeIds.addAll(traversal.order());
    depth = traversal.depth();
}
```

完整报告是"**料从哪来 + 货去哪了**"的总览，一次给全，适合现场排查时看整张子图。用 `LinkedHashSet`（而不是 `HashSet`）保证去重的同时保留插入顺序。

最后组装：

```java
// 只保留两端都落在谱系子图内的链路
Set<Long> subgraphIds = new HashSet<>(nodeIds);
subgraphIds.add(batchId);
List<TraceLinkVO> usedLinks = links.stream()
        .filter(l -> subgraphIds.contains(l.fromBatchId()) && subgraphIds.contains(l.toBatchId()))
        .toList();

BigDecimal totalQty = nodes.stream()
        .map(n -> BigDecimal.valueOf(n.quantity() == null ? 0 : n.quantity()))
        .reduce(BigDecimal.ZERO, BigDecimal::add);

return new TraceResult(direction, toBatchNode(batchById.get(batchId)), nodes, usedLinks, depth, totalQty);
```

"只保留两端都在子图里的边"这一步很关键——**BFS 命中了哪些节点，就只回传连接这些节点的边**，避免把整张全量图（可能几千条边）回传给前端。`totalQty` 是关联批次的合计数量，正向时代表"受影响的下游产出量"，反向时代表"投入的上游料量"——这是召回决策的关键数字。

最终结果结构：

```java
// framework/qms/trace/TraceResult.java
/**
 * 追溯结果。正向（召回）与反向（溯源）共用同一个结构，仅 direction 不同。
 */
public record TraceResult(
        QmsTraceDirection direction, // 追溯方向（1=正向追溯 2=反向追溯）
        BatchNode rootBatch,         // 根批次节点（追溯起点，不重复放进 nodes）
        List<BatchNode> nodes,       // 命中的关联批次节点（不含根批次），按 BFS 层序排列
        List<TraceLinkVO> links,     // 命中的关联链路（谱系图的边）
        int depth,                   // 追溯深度（根批次为 0，最远一层为 depth）
        BigDecimal totalQty          // 关联批次的合计数量
) {
}
```

## 七、Controller：追溯是只读查询

追溯没有 CRUD，`QmsTraceController` 只有三个 GET，挂在 `/api/admin/qms/trace` 下：`/forward`（正向召回）、`/backward`（反向溯源）、`/report`（正反合并的完整报告），每个都只收一个 `batchId`，分别调用 Service 的 `forwardTrace / backwardTrace / traceReport`。

前端拿到 `TraceResult` 后，把 `nodes` 画成节点、`links` 画成带标签的箭头（`fromBatchNo → toBatchNo`）、`rootBatch` 高亮，一张谱系图就出来了。王主任那次要翻三天纸的活儿，现在是 `GET /trace/forward?batchId=1` 一下。

## 八、边界与踩坑

**坑一：脏数据成环。** 有一次测试数据里出现了"投料 A→B、B→A"的环（两个操作员互相录反了），第一版 BFS 没防环，队列一路涨到几万，进程卡死。加了 `visited` 集合后，BFS 遇到已访问节点直接跳过，环不会导致死循环。但这个坑的根治不在 BFS，而在**录入侧拦截**——建边的 Service 应该校验"新边是否会在已有子图里成环"。BFS 防环是"兜底不死"，录入校验才是"从源头不产生环"。

**坑二：全量加载 links。** `selectListAll()` 一把把全表边捞进内存建图，眼下几千条没问题。但 README 里明确写了风险："大批量场景改用 PostgreSQL 递归 CTE（`WITH RECURSIVE`）"——真到几千万边时，**把 BFS 下推到数据库**，内存只装结果。当前 MVP 用内存 BFS 是"简单优先"，升级路径已经想好了。

**坑三：根批次不在任何边里。** 单独一个批次（还没投料、也没被投料），它自己不在 `qms_trace_link` 的任何一个端点里。第一版 Service 直接 `selectListByIds(endpointIds)` 时漏了根批次（endpointIds 里只有边的端点），导致"孤立批次"追溯报 404。修法是 `endpointIds.add(batchId)` 先把根批次塞进去——这个小小的 `add`，就是这段代码里最容易被忽略又最要命的一行。

## 九、商用化检查清单（追溯引擎版）

- `GenealogyGraph` 的 `visited` 防环验证过吗？故意造一个环状谱系，断言 BFS 不死循环、节点只出现一次。
- 录入侧校验过"新边不成环"吗？BFS 只是兜底，源头拦截才是根本。
- 全量 `links` 加载的性能测过吗？多少条边时内存和耗时会成为问题？
- `parent_batch_id` 的单级快查和边表的多级追溯，结果一致吗？（两者冗余，写入时要同一事务）
- 大规模场景的递归 CTE 版本验证过吗？`WITH RECURSIVE` 的深度限制和性能如何？
- 孤立批次（不在任何边里）追溯会报错吗？根批次是否被主动补进查询集合？
